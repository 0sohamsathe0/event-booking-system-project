CARDINALITY SUMMARY
-------------------
- One organizer user owns many events; each event has one organizer.
- One hall hosts many events; each event uses one hall.
- One category classifies many events; each event has one category.
- One event has many ticket types and bookings.
- One customer has many bookings; each booking belongs to one customer/event.
- One booking has one or more booking items and may have multiple payment
  attempts, but at most one successfully captured payment for its full amount.
- One payment can have multiple refund records within the captured refundable
  amount.
- One event has many status records and cancellation requests.
- One user receives many notifications.


STATUS SUMMARY
--------------
Event status:
- pending, approved, rejected, cancelled
- completed is derived from approved + end_datetime in the past

Booking status:
- pending_payment
- confirmed
- payment_failed
- expired
- customer_cancelled
- event_cancelled

Payment status:
- created
- authorized
- captured
- failed
- refunded (full refund; partial refund remains captured with refund records)

Refund status:
- pending
- processing
- processed
- failed


CRITICAL INTEGRITY RULES
------------------------
- available = capacity - reserved_quantity - sold_quantity
- capacity >= reserved_quantity + sold_quantity
- Payment confirmation moves reserved to sold exactly once.
- Failure/expiry releases reserved quantity exactly once.
- Only server-calculated amounts are sent to Razorpay.
- A Razorpay Order is created before Checkout.
- Checkout and webhook signatures are verified server-side.
- Duplicate callbacks/webhooks must be idempotent.
- External API calls must not occur while long database transactions hold locks.
- Refund records preserve the result even when a booking is already cancelled.
- No card number, CVV, UPI PIN, API secret, or other sensitive payment credential
  is stored in this database.
- Historical events, bookings, items, payments and refunds are not deleted.
